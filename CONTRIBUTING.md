# Contributing

How to build, check and change this formalization. The mathematical overview is in
[`README.md`](README.md); this file is about working on the code.

## Building

The toolchain is pinned in `lean-toolchain` (Lean `v4.33.0`) and Mathlib in `lakefile.toml`
(`v4.33.0`). With [`elan`](https://github.com/leanprover/elan) installed:

```bash
lake exe cache get   # prebuilt Mathlib oleans; skip this and Mathlib rebuilds from source
lake build
```

To compile one module while iterating, without building everything that imports it:

```bash
lake env lean Biyoneda/Unit.lean
```

`Biyoneda/Probe.lean` is gitignored and never imported. Use it as a scratch file for quick
experiments.

## Checking a change

`lake build` exiting 0 is **not** enough. A `sorry` is only a warning, and a coherence field
can be closed by an autoparam that rides on a `sorry` somewhere else, which looks exactly like a
real proof. CI therefore runs the same check you should run before committing:

```bash
lake build 2>&1 | tee build.log
```

```bash
scripts/verify-build.sh build.log
```

The script has three gates, and all must pass:

1. **Sorry ratchet.** The number of declarations using `sorry` must not exceed
   `.github/sorry-baseline` (currently `0`).
2. **Axiom gate.** Every declaration in `CLEAN_DECLS` (in `scripts/verify-build.sh`) must have
   its `#print axioms` output in the build log, and that output must not contain `sorryAx`. A
   check that is missing counts as a failure, not as a pass.
3. **Warning ratchet.** The number of warnings (not counting `declaration uses 'sorry'`) must
   not exceed `.github/warning-baseline` (currently `13`).

When a count **falls**, the script asks you to lower the baseline; do it in the same commit so
the ratchet keeps protecting. Raise the warning baseline only deliberately, and say why in the
commit message.

### Gating a new declaration

If you add a declaration that the theorem depends on, assert it in **both** places:

- a `#print axioms` line in `Biyoneda/CompositePairing.lean` (the file `open`s
  `CategoryTheory Bicategory Biyoneda`, so a short name works there), and
- the **fully qualified** name in `CLEAN_DECLS` in `scripts/verify-build.sh`, spelled exactly
  as Lean prints it in `'…' depends on axioms`, because that output is what the gate matches.

When you delete or rename a gated declaration, update both lists too. `CONTAMINATED_DECLS` is
empty and should stay that way; if something needs to go there, something has regressed.

## Code conventions

- **Module system.** Every file begins with the copyright header, then `module`, then
  `public import`s. A new module is built only if `Biyoneda.lean` imports it.
  `Biyoneda/BiCurrying.lean` is deliberately left out, so it is outside the build and every
  gate.
- **Compiler options** come from `lakefile.toml`: `relaxedAutoImplicit = false` and Mathlib's
  standard linter set. Follow Mathlib's naming and style conventions.
- **Use Mathlib first.** Before stating a lemma, check whether Mathlib already has it,
  including the component and reassociated forms generated by `@[to_app]` and `@[reassoc]`. A
  hand-written restatement of a Mathlib lemma should be deleted, not kept as a bridge.
- **`ForMathlib.lean`** holds general lemmas about Mathlib's own definitions that are missing
  upstream. Nothing in it may mention the Yoneda development, so that it can be lifted into a
  Mathlib PR as is.
- **Pick the right home.** General strong-transformation API goes in
  `StrongTransLemmas.lean`, evaluation coherence in `Evaluation.lean`, and so on; the module
  list in the README describes what each file is for.

## Dependency bumps

The Lean/Mathlib pin is a deliberate choice. A bump tends to break the hand-written coherence
fields, so treat it as a planned piece of work, not a routine merge. The weekly
`Update Dependencies` workflow only **opens an issue** reporting whether the next Mathlib
version builds; it never changes the pin itself.

## The paper

The write-up is `paper/Biyoneda.tex`. Compile it locally with `make` (requires TeX Live).
On pushes to `master` that touch `paper/*.tex`, CI rebuilds `Biyoneda.pdf` at the repository
root and commits it.

## Commit messages

Write an imperative subject line, then a body explaining what changed and why: which lemmas
were added, deleted or replaced, and by what. End the body with the build result, for
example:

```
Build: 0 errors, 0 sorries, 13 warnings, 127 sorryAx-free assertions, gate exit 0.
```
